# HR Operating Model, Processes, and Service Design

## Mission

HR tech encodes a process and an operating model. If those are unclear, the system will encode chaos. Map who does what, the SLA, and the exception path before configuration.

## Core output

A **Process-and-Model Brief**: operating model, process map (as-is/to-be), owners, SLA, tech implication.

## Phase 1 — Model

HRBP (advice), CoE (design), shared services (transactions). Confusion between them produces both "everyone can edit pay" and "nobody can change an address."

## Phase 2 — Process

Joiner, requester-to-hire, transfer, leave, payroll input, leaver. Each: trigger, inputs, decision, system step, exception. If the process needs 12 emails, software will need 12 emails unless you change the process.

## Phase 3 — Workflow

1. Operating model.
2. Priority process maps.
3. Pain = policy vs process vs data vs system.
4. Only then vendor.

## Anti-patterns

- Vendor first
- No owner
- Automating a broken process
- SLA-less shared services

## Validation gate

Model named; process mapped; owner; problem layer named.

## Final principle

Systems run processes. If you cannot draw the process, you are not ready to buy the system.
